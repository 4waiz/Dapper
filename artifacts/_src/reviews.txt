Abstract—This document supplements the main paper with the full reproducibility package, the complete benchmark table, the per-frame 
mode distribution, the scheduler risk score, and notes on scope. All values are consistent with the main manuscript and are produced 
deterministically by the released prototype with random seed 42. The benchmark is a controlled synthetic stress test, not a physical-robot 
deployment. 
S1. Reproducibility Package 
The prototype is a self-contained Python project: a 
deterministic 
scheduler, 
a 
runtime 
network 
monitor, 
local/edge/cloud perception simulators, an optional FastAPI 
edge-inference service, a command-line benchmark runner, a 
metrics module, a plotting pipeline, and unit tests. It runs 
without a physical robot or any external model download. 
Every result uses 500 frames per profile-policy pair, a 100 ms 
control deadline, and a fixed random seed of 42, so the 
benchmark is fully reproducible. The benchmark is controlled 
and synthetic. 
# from the dapper/ directory 
python -m pytest tests/ -q 
python benchmark.py run-all \ 
   --frames 500 --deadline-ms 100 \ 
   --seed 42 --out-dir results 
S2. Full Benchmark Results 
Table S1 reproduces the full benchmark of 10,000 frame-level 
decisions (5 profiles × 4 policies × 500 frames). Metrics: 
Mean/p95/p99 are per-frame latency (ms); Miss % is the 
deadline-miss rate; Conf. is the mean confidence proxy; BW 
KB is total offload bandwidth over 500 frames. The confidence 
values are simulated proxies, not the accuracy of a trained 
detector. DAPPER achieves a 0.0% deadline-miss rate in every 
profile; under congestion, edge-only and cloud-only each miss 
94.6% of deadlines. 
S5. Scheduler Risk Score 
DAPPER computes a normalised deadline-risk score in [0, 1] as 
a weighted sum of five signals — normalised RTT, packet loss, 
edge load, frame age, and a deadline-pressure term equal to the 
estimated edge round trip divided by the deadline: 
 
where w_r, w_l, w_c, w_a, w_d are configurable weights, D is the 
deadline, a_t the frame age, and Ĉ_E the estimated edge compute time. 
Two thresholds map the score to behaviour: above the degraded 
threshold the scheduler selects degraded-safe; above the local 
threshold it stays local-fast for predictable latency. In the 
remaining low-risk region the choice is confidence- and 
margin-aware: it keeps the frame local when the local model is 
confident enough, and otherwise offloads — pure edge-accurate 
when the estimated round trip fits the deadline with margin, 
hybrid otherwise. Every remote attempt is charged its access 
RTT and upload bandwidth, including attempts that are lost or 
arrive too late to be accepted. 
S3. DAPPER Mode Distribution 
Table S2 lists how DAPPER distributed its 500 per-frame 
decisions in each profile. The counts explain the 0.0% miss 
rate: DAPPER stays local or degraded-safe when the network 
cannot be trusted, and uses hybrid (freshness-gated edge 
refresh) when it is safe. Under outage it falls back to degraded-
safe on 452 of 500 frames, consistent with the main paper. 
S4. Additional Experiments 
The released prototype also supports two sensitivity studies that 
vary one factor while holding the rest fixed: a deadline sweep 
(varying the control deadline D) and a risk-threshold ablation 
(varying the local-risk threshold). Qualitatively, relaxing the 
deadline lets DAPPER use the edge-accurate path more often 
and raises p95 latency toward edge levels, while raising the 
local-risk threshold shifts frames from local-fast into hybrid and 
increases offload bandwidth. These trends are consistent with 
the placement logic in Section S5; exact values depend on the 
configuration and are reported with the released code rather 
than claimed here, so as not to extend the main benchmark of 
Table S1. 
S6. Honesty and Scope 
• 
Controlled synthetic benchmark — not a physical-robot 
deployment, real wireless interference, or a production 
edge cluster. 
• 
Confidence values are simulated proxies, not the accuracy 
of a trained detector such as YOLO. 
• 
Network conditions are seeded, parameterised profiles, not 
captured Wi-Fi/5G/edge traces. 
• 
Every remote round trip is charged access RTT and upload 
bandwidth, including lost or late attempts. 
• 
Future work: physical-robot validation with real DNN 
detectors, trace-driven networks, ROS 2 
deadline/lifespan/liveliness QoS integration, multi-edge 
server selection, energy- and privacy-aware offloading, 
and learned threshold adaptation.
